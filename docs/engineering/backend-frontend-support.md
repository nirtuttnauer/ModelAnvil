# Backend support for the frontend

11 October 2026. The React application calls authenticated Django APIs. Production does not load Storybook fixtures. This implementation closes the missing authoring/execution paths while preserving tenant/project checks, immutable revisions, checksummed artifacts, worker fencing and production qualification gates.

| Area | Supported behavior |
| --- | --- |
| Models / Training | Initialize reproducible untrained CPU character weights and tokenizer; select them in the existing worker training flow, which reads published text and commits actual changed candidate weights. Other existing worker runtimes retain their own contracts and qualification reports. |
| Evaluation | Atomically register 1–64 immutable cases; create a pending candidate/baseline comparison; explicitly execute checksum-verified CPU character bundles, persist actual outputs, scores, slice counts and 95% Wilson intervals. At most 32 generated tokens per case. Unsupported or corrupt bundles produce no invented scores. |
| Alignment | Execute real bounded CPU character DPO, Bradley–Terry reward head training, PPO RLHF and verifier RL from committed disjoint preference artifacts; persist measured checkpoints, actual candidate bytes and settled training-step usage. |
| RAG | Create a collection; paste or upload text; build source-linked chunks with spans/hashes and a pinned lexical index. Stable source identifiers create revisions; old indexes retain exact membership while revocation/tombstones still apply. |
| Context Lab | Atomically save ordered blocks and their budget; compile immutable versions with runtime text overrides, output reserve, content caps, overflow policy and per-block allocations. Counts are deterministic estimates including serialized role wrappers. |
| Data / Annotation | Valid canonical uploads, source-group preparation/publication, budget admission before upstream access, project-scoped qualified acquisition, cancellation/resume accounting, cached-byte publication recovery; annotation review/conflict/history/closure/export. |
| Jobs / Budgets / Audit | Project-scoped owner jobs and attempts, precise attempt filters, owner cancellation routes, durable audit/idempotency; accounting separates currencies/units and retains unknown prices. |
| Releases | Actual committed CPU weight bundle bytes and loading evidence when available; read-only SPDX inventory or protected committed SPDX artifact. Metadata-only candidates remain unverified. |

New write paths use the existing router. Alignment artifact pins require the `0007_alignmentrun_execution_pins_and_more` migration; the other authoring paths listed here require no additional migration:

- `POST /api/v1/model-versions/initialize-cpu/` — `{name, seed}`. Filesystem artifact backend only. Result is an untrained base, never a qualified model.
- `POST /api/v1/evaluation-suites/register-cpu/` — `{name, scorer_type, cases}`. Cases use `case_id`, `input_prompt`, `expected_output`, optional `slice`.
- `POST /api/v1/evaluation-runs/{run_id}/execute/` — optional `{max_tokens}`. Candidate and optional baseline are read from the pending run's pins.
- `POST /api/v1/knowledge-bases/{knowledge_base_id}/index/` — `{documents: [{title, content, source_uri?}], chunk_size?, chunk_overlap?}`. Local identifiers are never fetched. At most 2 MB UTF-8/import and 10,000 chunks/index; overlap is at most half the chunk size.
- `POST /api/v1/context-recipes/` — `{name, initial_version: {model_limit_tokens, output_reserve_tokens, budget_policy, blocks}}`. Blocks use `block_key`, `block_type`, `role`, `order`, `priority`, `content_template`, optional `max_tokens`.
- `POST /api/v1/context-recipe-versions/` — same version fields plus integer `recipe` and positive `revision_no` for an existing scoped recipe.
- `POST /api/v1/alignment-runs/register-preferences/` — `{name, samples: [{prompt, chosen, rejected}]}` registers one committed preference artifact. Register train and held-out sets separately; their prompts must be disjoint.
- `POST /api/v1/alignment-runs/{run_id}/execute/` — executes an actual validated pending plan with numeric model IDs and UUID `train_dataset_artifact` / `held_out_dataset_artifact` pins. Supports 1–100 CPU steps; completed replay reuses the verified candidate.
- `POST /api/v1/alignment-runs/{run_id}/cancel/` — invalidates running checkpoint/candidate publication and settles committed steps. See the [alignment contract](cpu-character-alignment.md) for recipe-specific refs, actual reward heads, input/hyperparameter bounds and usage semantics.
- `POST /api/v1/release-versions/{release_version_id}/sbom/` — commits/reuses verified SPDX bytes and returns an authenticated artifact download endpoint.

The canonical [OpenAPI document](../../contracts/schemas/openapi.json) describes these request boundaries. Engineers can author/execute; viewers can read and run read-only retrieval/context compilation. Source documents and recipes are tenant-wide collections; project-owned training/data/model/job artifacts keep project access and explicit grants.

Initial backend/frontend support verification, before the alignment extension: 630 Django tests ran successfully (627 passed, 3 environment-dependent skips); 121 frontend tests passed; Django/migration checks and production/Storybook builds passed. Verification uses the full Django suite, real localhost HTTP frontend-client and worker journeys, frontend unit/mock-isolation tests, production/Storybook builds, and browser checks against a separate temporary SQLite database. The live browser created a knowledge base, indexed source text, queried its actual chunk, authored/compiled context blocks and displayed their durable audit entries. New Storybook plays cover both authoring paths plus CPU initialization, suite registration and evaluation controls using explicit synthetic fixtures. Evidence is in `output/backend-verification/`.

Alignment extension verification: 658 Django tests ran successfully (655 passed, 3 environment-dependent skips); 126 frontend tests and 4 smoke tests passed. Production and Storybook builds passed. All three alignment action stories passed in the browser; the execution story reported zero accessibility violations. An isolated live UI registered preference bytes, executed eight DPO steps, committed changed weights, and produced a completion through the independent standard-library consumer. Local evidence is retained in `output/alignment-verification/` and excluded from source publication.

Local evaluation is the bounded character runtime, not evaluation of arbitrary GPU/Hugging Face candidates. Alignment now has a separate bounded CPU character optimizer and 14 integration tests with actual API journeys, including all four recipes and independent standard-library byte loading. This does not qualify arbitrary model families or hardware. Embedding generation/projection, generated RAG answers, model-driven context summarization, managed-storage qualification and production serving remain outside this implementation. PostgreSQL concurrency and accelerator qualification have separate existing checks/reports; the three environment-dependent tests skipped by the local full suite do not establish those capabilities.
