# TASK-5 review — 11 October 2026

The training browser now previews actual encoded samples and verified input pins before offering launch. The server reports independent prerequisite, recipe, published-data, tokenizer, runner, worker-memory, free-slot, local-storage and remaining-budget checks. Every blocker includes a corrective action. The preview itself creates no run, job or reservation.

Resolved inputs come from the same runtime resolver used by execution. Sample text and all token IDs are shown for up to five training rows. Requirements summarize the selected configuration/optimizer, CPU slots, declared minimum memory and projected checkpoint/candidate storage. Expandable details expose input digests and capacity/budget units.

Budget preview and reservation share the same period/commitment calculation. Launch locks the policy, repeats compatibility/capacity/storage/budget checks and atomically reserves exactly the requested sample passes. The browser submits a signed, principal-bound preview token with a ten-minute lifetime; changed input pins, selected resource revisions, project, policy or storage root invalidate it. Programmatic callers can omit the preview token for compatibility, but still undergo the full fresh preflight before allocation. Successful idempotent replay returns the original run even after capacity changes or token expiry.

Changing form inputs clears the preview and prevents launch. Late preview responses cannot restore a report for changed inputs. Preview results receive keyboard focus and announce their status; the launch action follows the checks. A rejected launch requires a new preview. A transient network failure retains the unchanged request/key for safe retry.
