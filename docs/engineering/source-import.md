# Verified local source imports

Datasets can publish canonical envelope JSONL, CSV records, JSON record arrays, DOCX main-body text and PDF text pages. The browser uploads original bytes with their SHA-256 and explicit media type, then invokes the existing project-authorized preparation action. CSV/JSON/DOCX use the standard library; PDF requires the optional pinned `requirements.documents.txt` dependencies.

CSV requires unique nonempty headers and consistent record widths. JSON requires an array of objects with unique keys and finite values. Select a nonempty string text field and optionally a nonempty string source-group field. Without a group mapping, the whole file stays in one protected split group. This avoids splitting related paragraphs or records across training and held-out data; multiple source groups are needed to populate multiple splits. Text is preserved exactly, including Unicode, quoting and line breaks. Empty text or invalid mappings refuse publication.

DOCX extracts main-body paragraphs, including paragraphs in tables, preserving tabs and explicit breaks. It excludes headers, footnotes, images, embedded objects and rendered page layout. It never follows document relationships or extracts ZIP files to disk. Duplicate archive entries, encrypted main XML, archives over 1000 entries or 16 MiB uncompressed, non-UTF-8 XML, DTD/entity declarations and malformed documents are refused.

Input is bounded to 16 MiB and 10,000 output samples. CSV additionally uses the standard parser's field limit. Each canonical row contains an original-source SHA-256, exact-text SHA-256, extraction version, source location (CSV logical record, JSON array pointer or DOCX paragraph path) and deterministic UUID derived from source bytes, mapping and location. Extraction settings and the source digest enter the preparation recipe hash. The committed source artifact links to the immutable manifest through existing lineage. Existing privacy, duplicate and protected-content preparation options continue to run on extracted envelopes through the API.

PDF uses `pypdf==6.20.0` in a separate Python process with isolated imports, a private working directory and no inherited application credentials. It executes no external image decoder. It accepts up to 100 pages, 1 MiB decoded content per page, 8 MiB aggregate decoded content and 8 MiB JSON output. Filter expansion limits apply before text extraction. A ten-second CPU limit, output file-size limit and fifteen-second parent timeout bound execution; timeout kills and reaps the parser. Linux additionally requests a 768 MiB address-space limit. macOS refuses `RLIMIT_AS`, so no hard memory-limit claim is made for this Mac; stream/page limits and process separation apply. This is parser process isolation, not a general code-execution security sandbox. See the parser's [security limits](https://pypdf.readthedocs.io/en/6.20.0/user/security.html) and [text-extraction guidance](https://pypdf.readthedocs.io/en/6.20.0/user/extract-text.html).

Each PDF page becomes one exact extracted-text sample with a one-based page reference. The entire PDF remains one source group. Parser version enters both row provenance and the preparation recipe. Encryption, malformed PDFs and pages without extractable text refuse the whole document, including mixed text/scanned documents; blank pages are not silently discarded. OCR is required separately. Extracted text ordering follows the parser, not a guarantee of visual reading order or complete table/image understanding. Missing pinned dependencies and parser failures produce fixed client-safe errors without parser diagnostics. Supported execution is presently POSIX; other platforms remain pending.

Optional `chunk_characters` (32–4096) splits single plain-text blocks into balanced nonoverlapping spans measured in Unicode code points. It retains every character, page/path and source-group identifier, and records parent sample/content references, source transformation version, chunk hashes and deterministic child IDs. Existing source character offsets are preserved; inconsistent offsets, multimodal/multiple blocks and conversation roles are refused. Privacy, quality, duplicate and protected-content checks run on source rows before chunking and again on child rows. Source and child drop reports stay separate, so source privacy/evaluation text cannot evade checks by crossing a chunk boundary. Output is capped at 10,000 rows and a conservative 32 MiB estimate before metadata copies; the final chunked manifest also has a 32 MiB cap. With chunking disabled, the historical publication shape is preserved.

`POST /api/v1/datasets/{dataset_id}/prepare/` accepts `source_format` (`jsonl`, `csv`, `json`, `docx`, `pdf`), `text_field` (default `text`) and nullable `group_field`. The declared format must match the committed media type. Canonical JSONL and documents refuse field mappings. Existing canonical preparation retains its original recipe and row shape. Invalid extraction returns a sanitized 400 before any manifest/revision is published; earlier upload/dataset records may remain for inspection. There is no automatic retry or deletion.

The [Mac evidence](verification/modelanvil-source-import-2026-10-12.json) includes actual frontend-client HTTP upload, publication and manifest download for all three added formats, original-byte/text/group verification, corruption/authorization regressions and a browser CSV publication visible in the Training dataset picker. Publication confirms extraction and lineage, not training or model-quality qualification. The browser corpus has three training rows and no held-out rows, so it does not qualify continued pretraining.

The [PDF Mac evidence](verification/modelanvil-pdf-import-2026-10-12.json) records actual four/eight-page repository PDF extraction, page/source provenance, real frontend-client HTTP publication and the browser's four-page immutable revision. The [chunking evidence](verification/modelanvil-text-chunks-2026-10-12.json) records 99 chunks from that four-page PDF, exact reconstruction/spans/hashes and an actual tokenizer/preflight pass without truncation. Character limits do not guarantee tokenizer limits for other data: training preflight independently checks the selected tokenizer. This single-source pilot has no held-out rows and establishes no model-quality gain. OCR, visual/list recipe composition, actual synthetic inference and a budgeted recoverable recipe worker remain pending in TASK-21. This bounded synchronous source-import increment does not satisfy the whole ticket.
